# Pre-deployment performance audit

Date: 2026-09-30 (Asia/Colombo). Scope: the current working tree of `aranya-next`, the Express API, Prisma queries and migrations, static media, and deployment configuration. Existing uncommitted changes were included in the review. Application source was not changed during this audit.

## Findings in brief

The local delay has two distinct contributors: expensive first requests in the development server, and application work that will also affect production. Warm local routes were much faster. The most substantial confirmed application issue is the homepage frame loader: it attempts to download 192 large images shortly after mounting, including on a visitor who never scrolls through the animation.

Priority meanings: **P0** = complete before release; **P1** = high-value optimization to prioritize before release; **P2** = measurement-led improvement, especially as traffic/data grows. Impact ratings are judgments based on the code and samples, not measured speedup guarantees. Phases 1–7 code are locally verified, with Phase 7 growth/provider deferrals recorded; search repair, hosting/staging and navigation budget acceptance remain open. Current statuses are recorded below (updated 2026-10-02).

## Measurements and their limits

HTTP samples used Node fetch against the existing localhost servers, sequentially, on 2026-09-30. Timings include server response and body consumption; they do not measure browser paint, hydration, navigation interaction, or Core Web Vitals. API reads did not mutate catalog or order data. No load test was performed against the connected database.

| Request | Earlier/cold sample | Warm sample | Interpretation |
| --- | ---: | ---: | --- |
| Frontend `/about` | 9,737 ms | 205 ms | Large first-request overhead; the route has no catalog API dependency. |
| Frontend `/products` | 5,904 ms | 208 ms | Consistent with development compilation contributing significantly. |
| Frontend `/products/ceylon-cinnamon-quills` | Exceeded the probe's 20-second deadline | 264 ms | The deadline aborted the audit probe, not an application timeout. |
| Frontend `/` | 2,098 ms | 226 ms | HTML response only; does not include downloading the frame sequence. |
| API `/products?limit=8` | 840 ms in the three-round probe; 1,111 ms in an earlier probe | 337–346 ms | Remote DB/query work remains material even with a local API process. |
| API `/products?limit=60&sort=bestselling` | 460 ms | 301–340 ms | Returned 24,800 bytes of JSON in the current dataset. |
| API product detail | 787 ms | 392–423 ms | Includes product relations and a separate rating aggregation. |
| API `/health` | 1,564 ms | 96–100 ms | This health endpoint queries the database; the difference suggests connection/DB warmup or network variability. |

These are small development-session samples, not medians, p95 results, or production benchmarks. They support investigating development compilation and DB warmup; they do not establish either as the sole cause.

Static media inspection:

- Desktop hero: **192 frames, 52.09 MiB** in total; the first 41 frames total **15.68 MiB**.
- Mobile hero: **192 frames, 27.74 MiB** in total; the first 41 frames total **8.37 MiB**.
- Poster: **312,926 bytes**. The first desktop frame is **409,562 bytes**.
- Local raw hero assets responded with `Cache-Control: public, max-age=0`.
- Local Next HTML was gzip-compressed. API samples returned no `Content-Encoding` or `Cache-Control` header. Compression/CDN behavior in the deployed environment still needs verification.

**Production build verification passed.** A same-drive isolated copy compiled, checked types/lint, and completed the Next production build. Two existing warnings remain in AdminProducts: a missing effect dependency and a plain image element. The original running project's `.next` was not overwritten. The isolated copy did not copy `.env.local`, and used the default localhost API; the final deployment environment still needs its own verification. Temporary test output was removed after the checks.

The production build reported first-load JavaScript of **133 kB for home, 127 kB for products, 144 kB for product detail, and 149 kB for admin**, with **87.4 kB shared**. These are Next build estimates, not complete browser transfer totals, and exclude the large frame sequence, later resources and runtime work. The JavaScript totals alone do not explain the tens of megabytes loaded by the hero.

Local production HTTP checks on a separate server returned warm responses of **91 ms for home, 121 ms for products, 92 ms for product detail, and 104 ms for about**. First sampled responses were 59, 313, 911 and 633 ms respectively. These are small, warm-DB local samples; a separate market-header probe overlapped them. They exclude browser paint/interaction and are not staging or real-user measurements.

Despite some detail routes appearing with a prerendering symbol in the build summary, the final prerender manifest contained only robots and sitemap. Tested page responses had private/no-store cache headers and request-specific script nonces. This confirms that full-page shared caching is not active for the tested storefront routes. A synthetic legacy `x-market=local` cookie changed frontend SSR market labels; it was only a rendering check, not verification of valid signed local-market prices or payment correctness.

## Recommended implementation order

Additional finding from Phase 4 review: **PERF-32 — production server-to-server CORS compatibility.** `backend/src/index.ts` accepts only an explicitly allowed Origin outside development; both existing private SSR fetching and the public server fetch omit that browser header. The current fixture does not enforce production CORS, so its passing cache checks cannot establish that deployment SSR works. Define a server-to-server request policy that preserves browser-origin rejection and authenticated-write protections, then test the actual production API with allowed, disallowed, absent and `null` Origin. This is an existing release blocker, recorded for Phase 8 rather than changing the security policy during a performance-cache phase. Existing backend-wide lint also fails on unused `_userId` at `backend/src/controllers/order.controller.ts:62`; release cleanup must resolve it. Neither issue was introduced by Phase 4.

1. Establish production measurements and add navigation feedback/time budgets (01, 05, 06, 30).
2. Fix the hero loader, animation work and initial image delivery (02–04, 11–13).
3. Fix public cache keys, primary/related rendering and invalidation (07–09, 23–24).
4. Reduce bootstrap work and client bundles (10, 14–18, 25, 29).
5. Improve payloads, query plans and host placement based on measurements (19–22, 26–28).

Preserve the existing design, USD/LKR behavior, server-authoritative cart totals, authentication rotation, RBAC, and payment transactions during implementation. These constraints shape the optimizations, not a request to redesign the UI.

## Release validation

- Test `/`, `/products`, one product detail, `/categories`, `/journal`, an article, `/recipes`, a recipe, `/gifts`, `/about`, search, account, cart and checkout. Exercise `/admin` separately.
- Measure hard reloads, first and repeated navigation, returning visits, slow mobile network/CPU, and rapid clicks while the hero loads. Phase 0 adds a local fixture browser baseline; live staging and the full scenario matrix remain outstanding.
- Proposed Web Vitals targets: **LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 at the 75th percentile**. Lab tests are a pre-launch screen; real-user percentiles require collected field data.
- Suggested project budgets, to confirm on staging: navigation feedback within 100–200 ms; warm common page content within approximately 1 s on the chosen test profile; warm public API p95 under 500 ms. These are proposed goals, not achieved results or universal web standards.
- Verify homepage frame requests stay bounded until the animation needs more, repeated visits reuse versioned assets, same-market guests share public-data cache entries, and markets/private user data remain isolated.
- Verify error and retry UI appears within the chosen deadline when the API is unavailable. Confirm no repeated mutation or payment request is introduced.

## Optimizations already present

- Standard storefront links mostly use Next Link rather than full-document reloads.
- Home featured/bestseller data and several other independent loads already use Promise.all.
- Public product/blog fetch wrappers already request time-based revalidation; the concern is cache partitioning/rendering/invalidation, not a total absence of caching.
- Product images use Next Image; generated marketing image slots use a different, less efficient path.
- Fonts are self-hosted with `next/font`; Next HTML compression is working in the local samples.
- Product ratings are batched; several relations/queries are bounded, and product listings support cursor pagination.
- Performance indexes already exist in migrations; Phase 0 verified the eight expected indexes are installed. Query plans still need verification.
- The root CommerceProvider already persists across routes, cart writes are optimistic, and quantity changes are debounced.
- Backend socket timeouts and shared 401 refresh logic already exist; explicit end-to-end deadlines and coordinated startup remain improvements.

- [Next.js 14 caching](https://nextjs.org/docs/14/app/building-your-application/caching): distinguishes Data Cache, Full Route Cache and Router Cache, including dynamic cookie behavior and GET request memoization.
- [Next.js 14 CSP nonce guidance](https://nextjs.org/docs/14/app/building-your-application/configuring/content-security-policy): a fresh nonce requires dynamic rendering.
- [Next.js 14 lazy loading](https://nextjs.org/docs/14/app/building-your-application/optimizing/lazy-loading): defer optional client components/libraries.
- [Express production performance guidance](https://expressjs.com/en/advanced/best-practice-performance.html): compression, caching and reverse-proxy delivery options.
- [Core Web Vitals thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds): good thresholds and their percentile-based interpretation.
